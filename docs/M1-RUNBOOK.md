# M-1 取证操作手册（Windows + 非越狱）

> 目的只有一件事：**在改动任何一行净化逻辑之前，先拿到"卡启动图"和"设置页闪退"的一手现场**。
> 这份手册对应的产物是 `BluedHushREA-dylib-m1`（源码 `M1Trace.xm`），它不含任何净化锚点，
> 不 swizzle 宿主的任何业务方法，只做：落盘日志、崩溃环形缓冲、主线程阻塞采样、锚点可达性清点。

---

## 0. 先明确"什么算成功"

拿到数据算成功的标志是——你能把下面三样交给我：

| 交付物 | 从哪来 | 说明 |
|---|---|---|
| `m1.log` | 电脑上跑 `tools\m1log_server.py` 自动收 | 冷启全过程时间线，最重要 |
| `.ips` 崩溃报告（若有） | 手机「设置 → 隐私与安全性 → 分析与改进 → 分析数据」 | 只有真崩了才有；卡住不崩时没有 |
| 你的操作时序 | 你自己记 | 「几点几分点了什么、卡在第几秒」 |

**看不到日志 ≠ 失败**：观测版会把同一份内容写进 App 沙盒的 `Documents/REA-M1.log`，
实在推不出来时还有兜底（见 §3.4）。

## 1. 装观测版（三种装法，按你现在的方式选一种）

产物在 GitHub Actions 的 artifacts 里，名字是 **`BluedHushREA-dylib-m1`**（不要拿错成 `BluedHushREA-dylib`，那是完整功能版）。

### 1.1 你原来用 LiveContainer 跑（最可能的路径）

1. 下载 `BluedHushREA-dylib-m1` 压缩包，解压得到 `BluedHushREA.dylib`。
2. 找到 LiveContainer 里这个 App 的实际安装目录（你之前注入 v12 时改过的那个位置），把里面的 `BluedHushREA.dylib` **整份替换**掉。
3. **不要叠加**：一个 App 的 `Frameworks` 里只留一份 `BluedHushREA.dylib`。如果你之前用「注入工具」追加过一条 `LC_LOAD_DYLIB`，那还是走同一条注入记录，只是文件换掉。
4. 重签（证书 + 描述文件必须和主 App 一致），重装，启动。

> 判断"到底加载了没有"：启动后马上看电脑端有没有 `[REA-Test] [M1] ctor entry`。没有这一行 = dylib 根本没被 dyld 加载，先解决注入，别往下走。

### 1.2 你用 Esign / Sideloadly 注入 IPA

1. `注入动态库` → 选新的 `BluedHushREA.dylib`
2. 注入路径保持不变：`@executable_path/Frameworks/BluedHushREA.dylib`
3. 与主 App 同证书同描述文件重签 → 安装

### 1.3 关键前提

- **观测版和 v12 的安装位置、注入路径、plist 完全一样**，所以"换不换观察员"在你的操作上只有一步：替换那一个文件。这也是刻意的设计——避免引入第二个变量。
- 首次启动时，如果你的 `purify_splash_mode` 还没被写过，观测版会把它写成 `0`（等于净化引擎全关）。**这一条是必须的**：我们要先看"完全不净化时 App 能不能正常起来"，这是整个二分矩阵的第 0 格。

## 2. 让日志实时流到 Windows（核心步骤）

非越狱机器上，Windows 抓 iPhone 的 NSLog 很不稳定（`idevicesyslog` 在 iOS 17+ 经常连不上），
App 沙盒文件也拖不出来（宿主 `Info.plist` 没开 `UIFileSharingEnabled`，我们也不能改它）。

所以观测版内置了一条**局域网日志通道**：裸 TCP（不走 `NSURLSession`，因此不受宿主 App 的 ATS 明文限制），每 2 秒批量推一次。

### 2.1 电脑端（一次就好）

在 `cmd` 里，仓库目录下：

```cmd
python tools\m1log_server.py
```

正常会打印：

```
M-1 日志接收端已启动
  监听 TCP : 0.0.0.0:8765
  监听 UDP : 0.0.0.0:8766（自动发现，手机端零配置）
  落盘     : D:\DeepSeek\hush\_work\m1.log
```

- 第一次运行 Windows 防火墙会弹窗 → **必须点「允许访问」**，并且勾上"专用网络"。
- 日志会**追加**写入 `_work\m1.log`，同时实时打在屏幕上。

### 2.2 手机端：什么都不用设

观测版启动后会自动往局域网广播 `M1-DISCOVER`，脚本收到就回 `M1-HERE 8765`，然后日志开始流。

**唯一要求：手机和电脑在同一个 Wi-Fi（同一网段，别一个连 5G 一个连路由器）。**

### 2.3 如果日志里出现 `UPLOAD discover fail`

原因只有三种，按顺序排查：

1. **脚本没跑 / 跑在另一台机器上** → 先确认脚本窗口还在。
2. **不在同一网段** → 手机 Wi-Fi 详情里看 IP，电脑 `ipconfig` 看 IP，前三段要一样。
3. **iOS 本地网络权限被拒** → 手机「设置 → 隐私与安全性 → 本地网络」里找到本 App（LiveContainer 或 Blued），把开关打开。这个权限一旦被拒，观测版**不会**弹任何提示，只会在日志里写一行 fail。

手动兜底：在手机上把 defaults 里的 `rea_m1_upload` 设成 `<电脑局域网IP>:8765`（例：`192.168.1.7:8765`），它会跳过广播直接用这个地址。

### 2.4 最后的兜底：沙盒文件

同一份日志也会写进 App 沙盒 `Documents/REA-M1.log`。如果三路都推不出来，你再告诉我，我给你一个"把日志塞进剪贴板/写进截图"的过渡版本——但先别急，通常 §2.1 + §2.2 就够。

## 3. 拿 `.ips` 崩溃报告（只有真崩了才有）

### 3.1 手机端直接取（推荐，不需要电脑）

1. 打开「设置」
2. 「隐私与安全性」→ 滑到底 →「分析与改进」
3. 「分析数据」
4. 在列表里搜 **`Blued`**，也搜 **`LiveContainer`**（LiveContainer 里跑的 App，崩溃可能记在宿主名下）
5. 找到时间对得上的那条（文件名形如 `Blued-2026-10-30-213045.ips`）
6. 点进去 → 右上角「分享」→「存储到"文件"」→ 存到你顺手的目录
7. 再通过 iCloud 云盘 / 微信文件传输 / QQ 传到 Windows

### 3.2 爱思助手取（可视化，但依赖驱动）

爱思助手连上设备 → 「工具箱」→「崩溃日志」（有的版本叫「崩溃分析」）→ 列表里找 Blued / LiveContainer → 导出 `.ips`。

### 3.3 注意

- **卡在启动图但没崩 → 不会有 `.ips`**。这种情况我们靠 `m1.log` 里的 `SCREEN` 时间线判断卡在哪一步，这本来就是观测版的主要目的。
- 如果 App 被系统杀掉（内存 / 看门狗），报告名可能形如 `jetsam` 或 `watchdog`，也一并发我。

### 3.4 观测版自己的崩溃现场

除了系统的 `.ips`，观测版还会在**信号崩溃的第一现场**把最近 160 行日志写进 `Documents/REA-M1-crash.log`，并继续经由局域网推出去（前缀是 `==== M1 RING DUMP`）。
这份东西比 `.ips` 更贴近现场——它记录了崩溃前 160 行到底在干什么。

## 4. 复现清单（照着点，我在后台看日志）

> 每一步之间**留 3 秒**，让我能从时间戳上切开。每步做完在心里记一句"第几步做了啥"。

### 4.1 冷启基线（不管你现在遇到的是哪个 Bug，这步最先做）

```
A0  杀掉 App 进程 → 清 LiveContainer 缓存 → 等 3 秒 → 启动
A1  盯住启动图：能不能进首页？进去用了多久？
A2  进首页后什么都不点，静置 30 秒
A3  杀掉进程 → 再启动一次（第二遍是热缓存，用于对比）
```

**这四步要回答的问题**：完全不净化时，App 本身能不能正常起来？
- 如果 A1 也卡 → 卡启动图**不是净化造成的**，而是别的东西（注入/签名/宿主自身/我们的观测层）。那我们省的就不是一天，是一周。
- 如果 A1 正常，只有开了净化才卡 → 直接锁定净化，进 §4.2。

### 4.2 卡启动图（Bug A）

```
B0  确认当前档位：日志里搜 "purify_splash_mode"，看它是 0 还是 1/2/3
B1  把它设成 1（只开默认档）→ 冷启 → 观察是否卡
B2  设成 2 → 冷启 → 观察
B3  设成 3 → 冷启 → 观察
B4  每次卡住后等满 15 秒（等看门狗/超时），再截图，再杀进程
```

每档之间必须：**杀进程 + 等 3 秒**，否则读到的是上一档的残留状态。

### 4.3 设置页（Bug B）

```
C0  进首页 → 点开「我的」→ 找到设置入口，但**先不要点进去**
C1  点进设置页 → 只停留 3 秒 → 立刻返回（不滚动）
C2  再进设置页 → 往下滚 3 屏 → 返回
C3  再进设置页 → 滚到底 → 点一个开关 → 返回
C4  如果闪退：重开 App，把崩溃前那段日志发我（观测版会把 ring 推出来）
```

**这三步是刻意的**：C1 只测"渲染我插入的那一行"，C2 测"滚动触发 cellForRow"，C3 测"点击回调"。
哪一个阶段先崩，直接决定是"行数/高度不一致"还是"选择子/回调"——这正是 §3.2 二分阶梯要分辨的东西。

### 4.4 通用注意

- 每次冷启前 **一定要先杀进程**，因为我们的很多状态是进程内静态变量，热启动会骗人。
- 卡住时**别急着划走**，等满 15 秒——要看门狗/超时日志出来。
- 一有问题就截图（带时间），截图和日志对得上，我才敢下结论。

## 5. 数据怎么给我

把这三样发我（能发多少发多少，缺的我会说）：

1. `D:\DeepSeek\hush\_work\m1.log`（整个文件，别删行）
2. `.ips`（如果有）
3. 一句话时序：「A1 卡了大约 8 秒才进首页；C1 进去就闪退」

我这边要看的判据（先告诉你，你可以自己验）：

| 现象 | 日志里应该出现 | 说明 |
|---|---|---|
| 观测层是否活着 | `[M1] ctor entry` | 没有 = dylib 没加载 |
| 主线程有没有被堵 | `[M1] STALL`（≥200ms） | 有 = 是"卡"不是"崩" |
| 卡在哪一屏 | `[M1] SCREEN vc=...` 的最后一行 | 停在哪就是卡在哪 |
| 疑似卡死 | `[M1] STUCK-CANDIDATE` | 广告类视图连续 2 秒不消失 |
| 锚点能不能全装上 | `[M1] ANCHOR miss ...` + 汇总 `ok/miss/total` | 这是审核 B1 的直接证据 |
| 是不是崩了 | `==== M1 RING DUMP` | 崩溃前 160 行现场 |

## 6. 如果什么都没收到（诊断树）

```
电脑端脚本窗口有没有 "发现请求来自 x.x.x.x" ?
├─ 有 → 手机能找到你，是 TCP 8765 被拦 → 防火墙放行 8765（入站，专用网络）
└─ 没有 → 手机根本没广播成功
    ├─ 日志里有 "UPLOAD discover fail" ? → 本地网络权限 / 不同网段
    ├─ 日志里有 "UPLOAD off（未设置...）" ? → 说明走的是手动分支但 key 为空，删掉该 key
    └─ 日志里连 "UPLOAD" 都没有 → 观测层没跑到 +0.30s，看有没有 "phase=install"
```

## 7. 这一阶段我**不会**做的事

- 不装任何净化锚点（`kPInstall` 一条都不装）
- 不改宿主任何业务方法的返回值
- 不删任何视图
- 唯一会写的 defaults 是 `purify_splash_mode = 0`（且仅当它不存在时）

换句话说：**M-1 的产物最多是"什么都没生效"，不会让 App 变得更坏**。这是刻意的——取证阶段最忌讳的就是"观察行为本身改变了被测对象"。
